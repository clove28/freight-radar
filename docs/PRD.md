## 1. 背景与问题

个体大货车司机接单时的真实痛点：

- 平台只显示运费，**不显示这一单跑下来到底剩多少**（油费、高速、空驶、杂费都要自己心算）；
- 回程能不能接到货、路线熟不熟、货主靠不靠谱，全靠经验；
- 跑完之后的账、损耗、证据（过磅/封条/卸货）散落在相册和脑子里，事后扯皮没有凭证。

目标：把「这一单值不值得跑」变成**可计算、可解释、可追溯**的决策。

## 2. 用户与场景

| 角色 | 诉求 | 本项目是否服务 |
| --- | --- | --- |
| 个体货车司机（主） | 快速判断一单值不值得跑；少空驶；算清账；留证据 | ✅ |
| 家庭/亲友（演示对象） | 看得懂、手机上能用 | ✅（移动端 Web） |
| 车队/车主（次） | 多司机、信用、统计 | ✅ 轻量（多司机 + 统计） |
| 货主 / 撮合平台 | 发布货源、结算 | ❌ 非目标（不撮合、不经手运费） |

核心场景：找货 → 算成本 → 比评分 → 接单存证 → 记账对账 → 形成历史画像 → 下次推荐更准。

## 4. 范围与优先级（P0–P17）

> 排序依据：**依赖链**（没有核心引擎就没有推荐）→ **风险**（金额/AI 边界先立规矩）→ **演示价值**（能讲、能看、能自证）。验收映射见 [验收标准](验收标准.md) §5。

| 阶段 | 目标 | 优先级理由 | 状态 |
| --- | --- | --- | --- |
| P0 核心引擎 | 成本/评分/过滤 + 数据层 + AI 编排 + API + 测试 | 一切的地基；金额公式必须先有断言 | ✅ |
| P1 移动端产品层 | React 前端 + 导航 + 三态 | 让司机能用；演示需要 | ✅ |
| P2 订单与决策增强 | 接单/证据链/损耗/证据包 + 底线偏好 + 价格异常 | 从「推荐」到「跑单留证」的闭环 | ✅ |
| P3 信用与个性化 | 货主信用 + 历史画像 + 真实货源 API 仓储 + 空驶真实化 | 解决「数据可不可信」，为 P4 提供真实成本口径 | ✅ |
| P4 路线与环境 | 高德路径/天气/POI + 路线策略 + 天气修正 | 成本/时长从估算走向真实；无 key 必须可演示 | ✅ |
| P5 持久化与决策增强 | JSON 持久化 + 路线偏好 + 多段天气 + 行情异常 + Docker | 数据不丢；首次具备部署能力 | ✅ |
| P6 持久化升级与账号 | SQLite + 多司机 + SSE + QuoteProvider | 并发/隔离；为登录与实时推送铺路 | ✅ |
| P7 登录与实时通道 | scrypt 登录 + WS + 行情 API | 多用户与实时提醒；安全基线 | ✅ |
| P8 账号安全与多端同步 | 会话 TTL + 短信验证码 + 鉴权中间件 + 同步 API | 上线前的安全门；多端场景 | ✅ |
| P9 登录体验与安全 | 扫码登录 + 短信限流 + 请求日志 | 演示体验与成本控制 | ✅ |
| P10 数据可视化与安全 | 统计 + 图表 + 登录锁定 + 密码强度 | 让收益可看；安全加固 | ✅ |
| P11 数据精确与对账 | 记账 km + CSV + Provider 抽象 + compose | 司机对账刚需；换供应商零改动 | ✅ |
| P12 收益账本页 | 账本页 + 记账 CRUD + CSV 列 | 把账本变成日常入口 | ✅ |
| P13 账本增强与容错 | 编辑 + 月度汇总 + 打印 + 高德降级 | 账本可用性；外部依赖容错 | ✅ |
| P14 真实 LLM 接入 | 真实模型 + JSON 容错 + 白名单 + 失败回退 + 限流 | AI 解释自然度；钱与数据边界不能破 | ✅（含 DeepSeek 迁移） |
| P15 报表与多端 | HTML 报表 + 分页 + 引擎徽标 + 小程序云端模式 | 报表与外部端接入 | ✅ |
| P16 高德真实数据 + 信用管理页 | 真实路线/天气/POI + 信用管理页 | 真实数据体验 + 信用闭环 | ✅ |
| P17 真实化冲刺 | 真实货源 API、短信/行情 Key、微信扫码、HTTPS、小程序真机、服务端 PDF | 上线最后一段，逐项 DoD（见 §6） | ⬜ |

## 5. 非目标（明确不做）

- **不撮合交易、不代收运费、不做支付/担保**；不构成运输合同（见 `deploy/免责声明.txt`）。
- 不接真实货源 API（P17 范围，当前为 Mock/演示对端）。
- 不做原生 App / 微信小程序真机（P17 范围；小程序为演示蓝本）。
- 不做多租户 SaaS 合规、不做发票/税务。
- 不在 LLM 侧做任何金额/评分计算或数据生成（架构红线，见 [AGENTS.md](../AGENTS.md) §2）。

## 8. 需求 → 验收 → 测试的追溯原则

- 每个 US 至少映射一个 UAT 或验收标准条目；没有验收方式的需求不开工。
- 涉及金额/评分的需求，必须有对应测试（[testing.md](testing.md)）。
- 新增/变更需求：先改本文件与验收标准，再改代码，最后补测试（同一主题一个提交）。
- 验收记录落在 `docs/验收记录/`，按验收标准 §12 模板填写。
