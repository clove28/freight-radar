# Phase 6：AI 能力边界

> 总原则：**AI 不创造事实。** AI 只负责理解、分析、解释和辅助决策；一切金额、距离、成本、状态、权限、排序、校验由程序负责。

## 一、程序负责（确定性，AI 永不参与）

| 领域 | 现有实现 | 状态 |
|---|---|---|
| 成本计算（油费/高速费/杂费/空驶/总成本/净收益/每公里） | core/cost.ts | 🟢 已实现 |
| 距离/里程 | 高德 driving / Mock 距离 | 🟢 已实现 |
| 利润/利润率 | cost.ts + services.ts | 🟢 已实现 |
| 司机底线过滤（每公里/单趟/运距） | scoring.filterCargoes | 🟢 已实现 |

| 评分（五维加权） | scoring.scoreCargo | 🟢 已实现 |
| 状态机（货源 open/taken、订单 accepted/onway/delivered/finished） | core/types + order.ts | 🟢 已实现 |
| 权限/登录锁定/扫码状态机 | core/auth.ts / scanLogin.ts | 🟢 已实现 |

## 二、AI 负责（理解与解释）

| 场景 | 现状 | V2 目标 |
|---|---|---|
| 自然语言理解 | 🟢 规则解析 DriverQuery + LLM | 保持 |
| 司机需求解析（"帮我找明天回武汉的货"） | 🟢 已有（时间/目的地/位置/车辆） | 增强多条件 |
| 货源推荐解释（"为什么这单最值"） | 🟢 已有（基于 ScoredCargo 真实数据） | 增加可信度解释 |
| 风险说明 | 🟡 部分（价格异常文案是规则，AI 可汇总） | AI 汇总证据链风险 |
| 卡友反馈总结（"这货主怎么样"） | ❌ 无结构化反馈 | AI 总结反馈，不编造 |
| 运输计划建议（"一路怎么安排"） | ❌ 无 | AI 基于路线/服务区/时间窗生成人话计划 |
| 饮食/补给建议 | ❌ 无 | AI 基于服务区 POI + 时间窗建议 |
| 异常情况辅助判断 | ❌ 无 | AI 辅助运营判断，最终运营决定 |

## 三、AI 禁止事项（红线）

- ❌ 编造运费/距离/成本/利润（必须来自程序）
- ❌ 编造货源/联系人/电话（必须来自数据层）
- ❌ 编造健康数据、做医疗诊断
- ❌ 擅自报警、替司机做承运决定
- ❌ 判定"货源绝对真假"（只能说证据支持度）

## 四、架构落地方式（现状已基本正确）

现有实现已符合原则：`assistant.ts` 的流程是 **NL → DriverQuery → 程序过滤/评分/排序 → LLM 只写解释**。V2 保持此流水线，扩展点为：

1. **给 AI 喂结构化事实**：LLM 输入只包含程序算好的 ScoredCargo/可信度/路线计划 JSON + 系统指令，AI 输出只允许"解释文本"。
2. **LLM 输出校验**：V2 建议对 AI 输出做关键词/数字抽查（若解释中出现系统未提供的数字 → 回退规则引擎文案），防止幻觉数字。
3. **兜底不变**：LLM 失败自动回退 RuleBasedLlm（已实现），保证无 AI 时功能可用。

## 五、三个示例场景的架构可行性（只分析，不开发）

| 场景 | 流程 | 现状 |
|---|---|---|
| "帮我找明天回武汉的货" | 解析（时间/目的地/位置/车辆）→ 调后端货源 API → 程序计算/筛选/排序 → AI 解释结果 | 🟢 架构已支持（DriverQuery 已含 to/maxKm/minPerKm/backhaulOnly 等） |
| "这单值得跑吗？" | 程序提供净收益/每公里/底线对比/价格异常/可信度/历史反馈 → AI 只解释 | 🟢 架构已支持（explain 接口存在，需补可信度数据） |
| "我明天跑杭州，这一路怎么安排？" | 路线和距离来自高德 → 程序生成途经点/服务区/时间窗 → AI 组装成计划文本 | 🟡 需新增运输计划数据源（高德途经点/服务区 POI），AI 侧无阻碍 |

**结论**：AI 边界现状健康（核心原则已贯彻），V2 不需要重构 AI 层，只需按新场景注入更多"程序事实源"。
