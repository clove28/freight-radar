# Phase 9：P0–P7 开发路线

> 每阶段以"**业务闭环是否跑通**"为验收标准，不写"做几个页面"。

## P0：业务模型与架构确认（本轮即完成）

- **目标**：确认 V2 定位、角色、闭环、数据模型、架构（= 本侦察报告）。
- **具体功能**：无代码开发；产出 docs/v2-research/ 全套报告。
- **需要修改的文件**：无（只新增文档）。
- **验收标准**：报告齐全，团队（含用户）对"平台定位 + 200 元服务价值 + 角色模型"达成一致。

## P1：司机核心闭环（可信度 + 服务费占位 + 结构化反馈）

- **目标**：司机从"搜索"到"付服务费接单"的最小闭环跑通。
- **具体功能**：
  1. 可信度分：core/credibility.ts（聚合 verified/信用/价格/完整度/更新时间）+ 货源卡/详情展示证据列表。
  2. 结构化卡友反馈：CargoFeedback（装货等待/装卸难易/入口提示）+ 提交/展示 API。
  3. 虚拟服务额度：ServiceFee 状态机 + 司机"确认承运"时扣减（余额不足提示充值演示）；明确不可提现。
  4. 角色模型落地：User.role + 司机端路由守卫（现有功能全部归 driver 角色）。
- **需要修改的文件**：constants.ts（加权重）、repository.ts（加接口）、mock/sqliteRepository（加实现）、services.ts（可信度/服务费编排）、app.ts（新路由）、web 货源卡/详情（展示可信度）。
- **新增模块**：core/credibility.ts、core/serviceFee.ts、data/feedback 实现、application/CredibilityService、application/ServiceFeeService。
- **依赖**：无外部依赖。
- **验收标准**：司机看到"货源可信度：91 + 证据列表"→ 反馈装货等待时长 → 接单自动扣虚拟额度 → 额度不足被拦截。**闭环成立**。

## P2：运营闭环（审核 + 对接 + 异常）

- **目标**：运营角色上线，"发布—审核—承运—对接—执行—回单—互评"环跑通。
- **具体功能**：
  1. 运营端 Web（ops-web/）：审核队列（联系货主 → 确认/驳回 + 留痕）、货源维护（补入口/停车/联系人）、订单异常队列、反馈审核、证据链查看。
  2. 装货执行信息结构化：loadAddress/loadEntrance/parkingArea/contactName 落 Cargo。
  3. 接单后运营对接流程：司机支付后 → 运营确认装货信息 → 推给司机（电话/入口/注意事项）。
  4. 回单/结算状态：订单加 settlementState（待回单/已回单/已结算）。
  5. 司机端展示"运营已确认"徽标与对接信息。
- **需要修改的文件**：types.ts（Cargo 扩展）、order.ts（状态扩展）、app.ts（ops 路由）、repository（Verification/OperationRecord）。
- **新增模块**：ops-web/（新前端）、application/CargoVerificationService、data/OperationRecord 实现。
- **依赖**：P1。
- **验收标准**：货主（演示账号）发一单 → 运营账号在后台电话核实并补全入口信息 → 司机付额度接单 → 收到运营确认的装货信息 → 执行证据链 → 回单 → 双方互评。**"200 元服务价值"可演示**。

## P3：货主/客户闭环

- **目标**：货源发布方/客户有正式入口（不再借司机端的"互助发单"）。
- **具体功能**：货主端（可先并入运营端）：发布货源（带装卸信息模板）→ 查看承运司机/运输状态 → 确认回单 → 评价司机。
- **验收标准**：货主全流程自助可用；客户角色（找车）随货主端一并评估，可后置。

## P4：AI 决策闭环增强

- **目标**：AI 在可信度/风险/计划三个新场景的解释能力落地。
- **具体功能**：
  1. "这单值得跑吗"：AI 解释纳入可信度证据与历史反馈。
  2. "明天回武汉的货"：多条件查询增强（已具备基础）。
  3. "一路怎么安排"：接入高德途经点/服务区 POI → 程序生成时间窗 → AI 组装计划文本。
  4. LLM 输出数字抽查（出现系统未提供数字 → 回退规则文案）。
- **验收标准**：三个场景均可演示，且 AI 解释中的数字全部能在结构化数据中找到来源。

## P5：运输执行（补给/加油/休息提醒）

- **目标**：运输中"该吃饭/该加油/该休息"的主动提醒跑通。
- **具体功能**：TransportTask（路线时间窗 + 服务区 POI + 车辆油耗估算加油点）+ 推送（SSE）；司机端行程时间轴。饮食建议只基于"服务区有无餐饮/热水/停车"数据，不做食材管理。
- **验收标准**：接单后生成行程计划，途中按时间/位置触发提醒；离线缓存基础订单信息（网络痛点第一版）。

## P6：安全守护（第一版）

- **目标**：独处风险的最小闭环跑通。
- **具体功能**：SafetyEvent 状态机（定时确认 → 提醒 → 升级应急联系人）+ 司机预设联系人 + 一键联系当地紧急服务（跳拨号）。**不做医疗诊断、不自动报警**。
- **验收标准**：司机长时间未确认 → 按预设联系人收到升级通知；司机主动确认则解除。

## P7：真实数据 Provider 预留

- **目标**：不接入，只把"可替换性"做实。
- **具体功能**：CargoProvider 接口统一（Mock/ExternalApi/Enterprise 三实现占位）+ 切换文档 + 对接规范（字段映射表）；真实支付 Provider 接口占位（不实现）。
- **验收标准**：Mock 换 ExternalApi 只需改环境变量（代码零改动），有联调桩可用。
