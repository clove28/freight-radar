# 货运平台 V2 最终重构报告

> 生成：夜间自动侦察（Phase 0–10 全部完成）｜详细证据见 docs/v2-research/phase-*.md

## 1. 当前项目真实状态

**一个健康、完整、可运行的"司机决策工具"Demo**：TypeScript strict + Express + node:sqlite + React，48 个 API 路由，191+3 测试全绿，AI 走火山方舟（实测可用），高德真实路线/天气，Docker 部署就绪。**但它不是"平台"**：没有运营角色、没有服务费、没有可信度体系、没有货主端、货源是 Mock（如实标注）。

## 2. 现有代码资产

- **确定性计算核心（最值钱）**：cost.ts（成本/净收益/每公里）、scoring.ts（五维评分+底线过滤）、credit.ts（+1/0/−3 信用）、order.ts（8 步证据链+损耗对比+价格异常）、constants.ts（集中调参）。
- **数据抽象（次值钱）**：Repository 六接口 + Mock/File/SQLite/Api 四实现 + Provider 模式（短信/行情/货源）。
- **AI 边界（原则正确）**：LlmPort + 规则兜底 + 程序算数、AI 只解释。
- **前端（可演进）**：司机端 6 tab 完整。

## 3. 真实用户痛点（跟车调研）

① 货源不可靠（最高优先级）② 装货沟通困难 ③ 长途吃饭难 ④ 独处安全风险 ⑤ 车载网络不稳。详见 phase-02。

## 4. 用户角色

**货源发布方 / 平台运营 / 卡车司机 / 运输需求客户** 四类。**运营不是普通 Admin**，是"200 元服务费价值"的执行者（审核、对接、异常、留痕）。现状：无角色模型。

## 5. 核心业务闭环

发布 → 运营审核 → 搜索 → 数据分析 → AI 决策 → 司机定夺 → **支付约 200 元服务费** → 运营对接/装货/运输/补给/安全/卸货/回单/结算 → 数据反馈 → 帮助下一次决策。详见 phase-04。

## 6. 司机 200 元服务价值

**买的是"平台背书 + 有人协助执行 + 证据兜底"，不是"一个电话号码"**：货源审核（可信度）、运营对接（装货信息/入口/停车）、异常介入、全程证据链、回单结算协助。

## 7. 货源可信度体系（核心差异化）

零件已有（verified/信用分/价格异常/时间戳），**缺聚合算法**。建议：core/credibility.ts 纯函数聚合——货主认证 15 + 运营确认 30 + 历史成交 15 + 卡友反馈 15 + 价格合理性 15 + 信息完整度 10 = 0–100 分 + 证据列表。**可信度≠真实性保证**，AI 只分析证据。

## 8. AI 能力边界

- 程序负责：成本/距离/利润/排序/评分/底线/状态机/权限/服务费/证据链/校验。
- AI 负责：NL 理解、推荐解释、风险总结、反馈总结、计划建议、补给建议。
- **红线**：AI 不创造事实（不编运费/距离/成本/货源/健康数据）；不做医疗诊断；不擅自报警；不替司机做决定。现状原则已贯彻，V2 只加"事实注入 + 数字抽查回退"。

## 9. 数据模型

现有 5 模型（Vehicle/Cargo/Order/DriverPreference/Credit）**复用 + 加字段**；现有基础上拆出 OrderEvidence/CargoFeedback；全新：User/Driver/CargoVerification/TransportTask/ServiceFee/OperationRecord/SafetyEvent。详见 phase-05。

## 10. 技术架构

Frontend（司机端/运营端/货主端）→ API（角色路由守卫）→ Application Service（新增编排层）→ Domain/Core（只增不改）→ Repository（新增接口）→ CargoProvider（Mock/ExternalApi/Enterprise）。AI 位于"解释路径"上，不在"计算路径"上。**单机 SQLite 部署支撑到 P5，不做微服务化**。详见 phase-08。

## 11. 当前技术债

- **P0（本轮）**：无角色模型；订单证据是布尔不是实体；无运营留痕。→ 已在模型/架构设计里给出方案。
- **P1**：可信度零件分散未聚合；app.ts 路由与服务编排耦合（V2 用 application 层解耦，不重写）。
- **P2**：前端单端（无运营端/货主端）；SQLite 迁移用 PRAGMA 补丁式（新增表后建议改为版本化迁移）；时间处理用"今天/明天 HH:MM"字符串标签（真实版应换时间戳）。

## 12. V2 缺口

最大缺口**不是算法，是"平台另一半"**：运营角色与闭环、服务费、可信度聚合、货主端、结构化卡友反馈、运输执行提醒、安全守护。逐项见 phase-07 总表。

## 13. P0–P7 开发计划

P0 模型确认（本轮）→ P1 司机闭环+可信度+服务费 → P2 运营闭环 → P3 货主/客户 → P4 AI 增强 → P5 运输执行提醒 → P6 安全守护 → P7 真实 Provider 预留。**每阶段以"业务闭环跑通"为验收**。详见 phase-09。

## 16. 哪些东西现在不要做

❌ 大规模重写后端 / 删除核心模块 / 重写 cost 与 scoring / 重写订单系统；❌ 爬取第三方货源平台 / 伪装真实全国货源；❌ 真实支付 / 真实健康数据 / 运营商流量接入；❌ 虚拟货币化（服务额度不可提现/转账/兑换）；❌ 微服务化 / 队列化；❌ 为 UI 改业务逻辑；❌ 无业务价值的 AI 堆砌。

## 19. 最终产品定位

> **货运雷达 = 面向个体大货车司机的 AI 货运决策与运输执行平台。**
> 平台帮助司机判断"这单值不值得跑"（客观数据 + 平台验证 + 运营协助 + 卡友经验 + AI 分析），并在司机决定承运后，协助司机把这一趟安全、有据、省心地跑完。
> 平台不承诺赚钱/绝对真实/零风险——**最终决策永远在司机自己手里**。
